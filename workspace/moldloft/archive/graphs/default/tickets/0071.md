Bug: a `forward` segment hits `_ => {}` in parse_event, so a forward-only message is dropped and he never sees it.

Do: when a message has a forward segment, use data.content if present, otherwise call get_forward_msg with {message_id: data.id}. Render the nodes into the envelope text as a bounded quoted transcript, e.g. `[合并转发 N条]` header then `名字: 内容` lines (card, else nickname), reusing the same segment renderer so images etc. become placeholders. Nested forwards: expand to depth 2, deeper ones become `[合并转发 N条]`. Caps on node count and characters with a visible `…(省略 K 条)` marker. Fetch failure or timeout keeps the message with `[合并转发，读取失败]` instead of dropping it. parse_event is sync today: the fetch needs the QqHandle, so either resolve in an async step after parse or have the inbound path enrich envelopes; do not issue an action from inside the socket task's select loop in a way that deadlocks on its own reply.

Acceptance: unit tests for inline content, fetched content (fake action), nesting cutoff, caps and fetch failure; a forward-only message produces an envelope; an ignored live test resolves a real forward id (env FORWARD_ID) read-only.
