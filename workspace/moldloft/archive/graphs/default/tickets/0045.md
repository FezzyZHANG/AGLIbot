Owner feedback 2026-11-01 after trying #30 in Telegram: replies are fast, but there is no debounce window, so messages sent in a row get separate replies; #30 only merges messages that queued up while a reply was in flight.

After an inbound chat message, wait for the chat to go quiet (default 2.5 s since its last message) before replying, restarting the timer on every new message from the same chat, capped at 10 s from the first message. Owner slash commands skip the wait. Events from other chats, Ticks and JobDone keep arriving into the queue during the wait and are handled in order afterwards; nothing is dropped.

Done when: three owner messages sent about a second apart produce one reply addressing all three; a single message is answered about 2.5 s later; a command is answered immediately.

Owner follow-up 2026-11-01: the waiting behaviour must be configurable, and preferably adaptive.
- Configurable: quiet window, cap, and the adaptive parameters below, all as config keys with code defaults; 0 disables the window. Exact YAML lines go in this ticket for the owner (config/ is L4).
- Adaptive (simplest first, with logging): per chat, an EWMA of gaps between consecutive messages within a burst (gaps longer than the cap start a new burst and are not counted). Quiet window = clamp(factor x EWMA, min, max); fall back to the default window until there is history. Log the window used and its basis for every batch so the owner can tune. Parked: punctuation/length heuristics to end the wait early.
