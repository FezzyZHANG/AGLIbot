+ title: "Make task attempts and completion handling idempotent"
+ status: "open"

+ description:
+ Low-priority extension of #29 for duplicate callbacks and stop/retry overlap. Implement when concrete duplication appears or overlapping/automatic attempts become part of normal use; do not make this an urgent single-job hardening project.
+ 
+ Scope:
+ - Give each actual execution a durable attempt identifier, carried by Job and Outcome. A continuation of the same live execution retains its identifier; a deliberate restart gets a new one. Repeated start requests while that attempt is active do not launch another worker.
+ - Revoke the attempt on stop/freeze/replacement. Verify the identifier before changing board status, clearing the active job, exiting flow or enqueuing the owner's result notification.
+ - Record acceptance of a terminal outcome so receiving the same current outcome twice does not repeat those state transitions or enqueue a second notification. A result from a revoked or older attempt must not overwrite current state.
+ - When replacing a worker, establish that the previous activation has stopped before launching another writer. Keep an unresolved stop visible instead of reporting successful takeover.
+ 
+ Acceptance: deterministic tests cover duplicate start, duplicate completion, completion queued just before stop, and an old completion arriving after restart; only the current accepted outcome changes state and produces a notification entry. Existing single-job behavior remains simple. A persisted accepted outcome survives reload without being applied again.
+ 
+ Delivery boundary: preventing duplicate local notification entries does not by itself guarantee exactly-once network delivery. Preserve unknown delivery outcomes for reconciliation under #35 rather than silently resending.
+ 
+ Non-goals: a general team scheduler, multi-process coordination, new review gates or artifact review digests.
+ tech_notes:

### ticket new:followup_idempotency (created)

+ title: "Deduplicate follow-ups across delivery and task resumption"
+ status: "open"
+ priority: "low"
+ group_name: "Ops"
+ parent_id: 29
+ description:
+ Low-priority extension of #29, built on the follow-up/session-continuation behavior in #33 (which already depends on #32). Add the smallest receipt mechanism needed when actual retry or duplicate-consumption problems appear; a shared team mailbox is not required.
+ 
+ Scope:
+ - Assign each follow-up a stable input ID and preserve it across transport retries. Repeating the same input ID must not append the same instruction twice; two distinct user messages with identical text remain distinct.
+ - Keep persisted, delivered-to-worker and consumed-at-a-step-boundary states distinguishable. A successful queue/write/host response is not proof that the worker processed the input.
+ - Persist the consumed-input checkpoint together with the resumable task-step record. Re-reading the file or reloading the same checkpoint must not reapply an already consumed instruction or trigger a second re-plan for it.
+ - If a crash leaves consumption uncertain, reconcile the worker session/checkpoint before replaying an instruction with external effects. Retain a pending/unknown state when it cannot be determined; do not claim exactly-once behavior across an uncoordinated external boundary.
+ - Associate input handling with the appropriate task execution/continuation so obsolete callbacks cannot consume inputs intended for the current work.
+ 
+ Acceptance: duplicate delivery of one ID is deduplicated; separate equal-text messages are retained; repeated step-boundary reads do not reapply a consumed input; failed delivery remains pending; reload preserves a committed consumption checkpoint; an uncertain crash window stays explicit.
+ 
+ Non-goals: arbitrary worker-to-worker chat, distributed leases, extra reviewer agents or review-version locking.
+ tech_notes:
+ AGLI touchpoints: #32 task origins and followups.md; #33 research step boundaries and delegated session continuation; src/work/board.rs and src/work/research.rs.
+ 
+ Reference: https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L514 (delivery lease, deliveredAt, readAt); https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L324 (discard obsolete mail, deliver, then record acceptance or release the delivery claim).
